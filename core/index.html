Velta Core

The messaging engine inside every Velta app is the chatmail core — the same open-source library that powers Delta Chat — vendored in our tree as core/. The copy we ship today is 2.69.0 (upstream license MPL-2.0). On top of that tag we keep a numbered patch series, re-applied every time we take a new upstream release.

This page is a stable map of what those patches do and why they exist. The living source of truth is on GitHub: VENDORISSUES.MD documents each patch, and tools/apply-core-patches.py is the quilt that applies them. COREUPDATE.md is the upgrade checklist. We do not edit core/ by hand — a re-vendor would silently drop a fix that is not in the quilt.

The current series is 200 operations. When upstream ships the same behavior, we drop the patch. That already happened once: an animated-WebP fix (#7) came out of our quilt when chatmail core 2.63.0 included it. For the relay software, see Velta Relay.

Relays you choose

Velta lets you keep more than one relay, pick which one sends, pause one without deleting it, and see what each relay can do. These patches make that product work.

#10 — Name the sending relay #163
What. The connectivity report names the relay the SMTP loop is actually using.
Why. After a failover the app can show the real sending relay, instead of the one that was last configured.
#11 — Pin a relay for sending #164
What. “Use for sending” puts your chosen relay first (ui.velta.send_transport).
Why. You pick the sending relay; the core should not silently prefer whichever one succeeded last. A pin that just failed is tried later for five minutes, so one timeout does not block every reconnect.
#15 — Relay capabilities #168
What. The app can read each relay’s advertised features — calls, push, iroh, and the rest.
Why. The Relays screen can show what each of your relays actually supports, without placing a test call or guessing.
#16 — IDLE, compression, and the recipient limit #170
What. The same per-relay metadata also carries IMAP IDLE, compression, and the SMTP recipient limit.
Why. The Relays screen can show instant delivery and the send limit from a real session, not a probe.
#23 — Extra relays are opt-in #284
What. The core no longer quietly adds extra relays after setup. “Add relays automatically” is a switch, off by default.
Why. Velta’s rule is relays you pick. A profile stays on the ones you chose unless you turn automatic adding on.
#24 — Pause a relay #189
What. You can disable a relay without deleting it. Sending and the inbox skip it; a live sending connection on that relay is closed.
Why. A misbehaving relay can be stopped now, without losing its address.
#30 — Strict pin #288
What. “Only send via the pinned relay” turns failover off for sending. Receiving stays multi-relay. The option does nothing unless a pin is set.
Why. When you need a specific sending address, the core must not silently switch to another one.

Staying responsive

Several patches stop a long IO restart or a slow database write from freezing the rest of the app.

#12 — A bounded push wake-up #165
What. A push fetch gives a dead socket ten seconds, then restarts IO and tries again.
Why. A half-open IDLE connection could otherwise block a wake-up for a minute, and the chat list looked frozen.
#13 — Push-token events #166
What. The core tells the app when a relay accepts or rejects a push token, including the relay address.
Why. The Relays screen and diagnostics can show whether push actually registered, instead of only writing it to a log.
#17 and #21 — Don’t hold the accounts lock across IO #175, #181
What. Network checks and start/stop-for-all-accounts release the accounts lock before waiting on an IO restart.
Why. Opening a chat or listing messages was waiting behind a shutdown that can take tens of seconds.
#18 and #27 — Interrupts that don’t queue #176, #244
What. Scheduler interrupts skip a lock held by an IO restart, and a skipped wake is delivered when the scheduler starts again.
Why. Sending a message or marking one seen was timing out while IMAP and SMTP tasks wound down.
#22B — The config cache no longer blocks every RPC #229
What. Config reads no longer wait on a lock held across a SQL write.
Why. Almost every request reads config, so a slow write was freezing the whole app.
#25, #26 and #28 — Stall follow-ups #241
What. Relay metadata is stored without holding the cache across the network; config cache fills can’t resurrect a stale value; the connectivity report says “Connecting…” during an IO restart instead of waiting.
Why. These were the remaining ways a restart or a heavy database write could blank the Relays screen or hang a chat.

Features and encryption

#14 and #29 — Reply-thread queries #167, #250
What. The core can return reply counts and reply ids for a chat, looking the quoted message up by its Message-ID.
Why. The “N replies” chip and the thread overlay need exact counts, including messages that are not on screen, without a slow rescan on every restart.
#19 — Admin groups #177
What. A group can have one admin who alone changes members, settings, pins, and other people’s messages. The wire format is the one used by ArcaneChat.
Why. So Velta and ArcaneChat can interoperate on admin groups. A short plan, including how stock Delta Chat clients see these invites, lives in docs/core-patches/admin-groups-plan.md.
#20 — Database encryption at rest #178
What. The account database can open with a key from the OS keystore, instead of always using an empty passphrase.
Why. The core still has a SQLCipher path, but the account manager was not passing a key, so an encrypted database never unlocked.
#22A — Attachment encryption at rest #178
What. File attachments are encrypted on disk in seekable chunks, under a key derived from the same profile key. Ordinary plaintext files still open and are migrated in place.
Why. Encrypting the database is not enough if media sit as plaintext files next to it.

Planned work

Open issues labelled core patch are the queue. The detailed write-ups stay on GitHub; this is the short list.

  • #391 — Send failover and retry. Try the next relay in the same burst for connect problems and relay-class errors, instead of waiting or failing that message at once. Remember a dead pin across a restart, keep the last SMTP response on the bubble, and stamp which relay actually sent (or last failed).
  • #392 — A per-message relay picker. A tray above the composer chooses the relay for this message only. The usual pin remains the default. Needs a per-message transport binding in the core.
  • #393 — Relay reputation. Score each relay over a ten-hour window, per network, and use that score to order relays (still behind your pin, unless the pin is backing off).
  • #394 — Retry with another relay. On a failed bubble, retry the same message on a different relay — automatically the next-best one, or one you pick in the tray.
  • #352 — Core size is research: what the vendored core actually weighs on Android, and which options would shrink it.

Related relay-side work, including a shorter retry queue so the app can offer #394 in minutes rather than days, is tracked as #395 and described on the Relay page.

The browser copy

The PWA needs the same core compiled to WebAssembly. That is a separate, opt-in series in docs/research/wasm-patches, applied on a copy of core/ rather than onto the production tree. Native Android and desktop builds stay on the quilt above.
