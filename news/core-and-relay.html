Why Velta changes the chatmail core and relay

18 November 2026 · 3 min read

We vendor the chatmail core and keep a public fork of the relay, with a short, documented set of changes on top of both. Here is why. The living lists stay on GitHub; velta.cc/core and velta.cc/relay are the public maps.

Velta is a client for the chatmail stack. The messaging engine is chatmail/core, the same library that powers Delta Chat. Mailboxes are chatmail relays. We are glad that work exists, we stay current with it, and we remain an independent client — not affiliated with the Delta Chat project.

The engine we ship is a vendored copy of that core, today version 2.69.0, sitting in core/. Every time we take a new upstream tag we re-apply a numbered patch series, currently 200 operations, with one script. The relay software we document is a public fork, pbuzdin/relay, and we merge upstream into it regularly — most recently on 17 November 2026.

We change things for two product reasons.

Relays you choose

Velta lets you keep more than one relay, pin one for sending, pause one without deleting it, and see what each relay can do. Soon it should also let you pick a relay for a single message, and retry a failed send on another one. That is a different product from a core that quietly replaces failing relays for you. Both are reasonable. Ours needs a small quilt: a sending pin, a strict-pin option, a pause switch, per-relay capabilities, and a few hooks so the app can show which relay actually sent.

The relay fork follows the same idea on the server. Signup is invite-only. Browser clients reach the mailbox through a WebSocket tunnel, because a browser cannot open raw IMAP or SMTP. After a message is accepted, though, onward delivery can still sit in a queue for up to two days. That is a sensible default for email, and a poor fit for chat. The next step, tracked as #395, is a queue of about an hour and a delay warning after five to ten minutes, so the app can mark the send failed in time and offer another relay.

Fixes we needed, and patches we drop

The rest of the quilt is more ordinary. Some patches stop a long IO restart or a slow database write from freezing the app. Some add a feature we needed — reply-thread queries, admin groups (a port of ArcaneChat’s format so the two clients interoperate), encryption of the database and of attachments at rest. None of this is a secret fork of the protocol. When upstream ships the same behavior, we take it out of the quilt. That already happened with animated WebP, once chatmail core 2.63.0 included the fix.

We do not edit the vendored tree by hand. A re-vendor would silently lose a fix that is not in the script. The script, the intent of each patch, and the upgrade checklist live in the Velta repository, and we update them when the patches move.

A short page, and a list that can change

A news post is a poor place to keep a list of twenty patches. It would be stale the next time we add one. So the detailed lists stay on GitHub, and two short pages on this site point at them:

  • velta.cc/core — what the current core patches do, why they exist, and the open issues for failover, a per-message picker, relay reputation, and retrying on another relay.
  • velta.cc/relay — what the relay fork adds on top of upstream, why, and the sending-reliability work in #395. Issues are disabled on the fork, so that work is tracked in the Velta repo.

If you want the living source of truth, start with VENDORISSUES.MD, tools/apply-core-patches.py, and the fork’s docs/compare.md.
