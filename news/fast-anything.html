We profiled Velta's web layer for the 5% worth rewriting

23 November 2026 · 5 min read

There is a popular promise in tooling right now: don't rewrite your app in Rust — profile it, find the 5% that's slow, port just those functions, and prove the ports behave identically. We liked the shape of that promise enough to run it against Velta's web layer with fast-anything: the markdown renderer, the message-history pipeline, and the folder-zip engine. Here is everything it found, including the part it refused to do.

The setup

Velta's desktop app is a build-less web UI in a system WebView, with the messaging core linked in-process as Rust. That already matters for this experiment: the heavy lifting — encryption, the network stacks, the database, the transfer engine — is not JavaScript. What remains in JS is interface glue: renderers, formatters, pagers. Exactly the layer where "rewrite the slow 5%" should have nothing to say. We wanted that confirmed with instruments, not vibes.

fast-anything's loop is: run your app under a profiler, rank functions by time spent × portability, record real calls to the hot ones, generate a one-function Rust crate, verify the port replays every recorded call bit-identically (plus derived edge cases — NaN, empties, non-ASCII, much larger inputs), and bench original against port. If the port is correct but slower, it refuses to enable it. We fed it three real workloads: the markdown renderer that builds every message bubble, the paging and timestamp functions that run on chat open and scroll, and the STORE zip engine behind folder transfers.

The numbers

  • Markdown bodies: 0.36 ms per message. A 2000-message open spends 33 ms rendering every body it will ever show. Nothing to port.
  • Timestamps (time, day separators, <time> tags): 5.8 µs per row. Nothing to port.
  • Paging windows (which slice of a 100,000-message history to fetch next): 101 µs per decision — an indexOf linear scan over the id array. A Rust port verified bit-identical on 800 calls and then measured 177× slower per call: every call marshals the whole 100,000-string array across the language boundary. The tool declined to enable it and said so.
  • CRC-32 (the checksum inside folder zips): V8's JIT already runs the textbook table-driven loop at ~600 MB/s, and a faithful naive Rust port ties it at 1.0×. Replacing the algorithm instead of the language — slicing-by-8, eight bytes per step — gave a verified bit-identical port at 4.5× per call, about 2.7 GB/s.

Three things the experiment taught

V8 is genuinely good at hot numeric loops. The textbook CRC in JavaScript is memory-bound on table lookups, and the JIT keeps up with naive Rust byte for byte. "Rewrite it in Rust" bought nothing until we rewrote the algorithm — and a better algorithm in JavaScript would have bought the same 4.5×. The win was never about the language.

The boundary is the bill. Crossing from JavaScript into Rust with 100,000 strings costs 8 ms — 80× the work itself. For functions called with small arguments thousands of times, a port is a pessimization wearing an optimization costume. The only ports that pay carry large, chunky work per crossing.

Velta's web layer has nothing to port, and that is the finding. Every hot path we could name is either DOM-shaped (the interface), already native (the core), or so cheap that the profiler needs a magnifying glass. The slow parts of a messenger are not the parts you can port: they are what gets fetched, when, and over which network — which is where our current performance work actually lives.

What we keep

  • Method: profile with instruments before touching anything; we will reuse this harness on future workloads.
  • A verified slicing-by-8 CRC on the shelf — if folder transfers ever feel slow on giant folders, the right integration is a Tauri command that zips in the shell, and the hard numbers to justify it already exist.
  • Respect for a tool that verifies its claims and publishes its failures alongside its wins. The "177× slower, declined to enable" verdict is worth more than a hundred benchmark banners.

The next performance work you will notice in Velta is not a language rewrite. It is a second device that finishes catching up before you have put the phone down — that work is scoped and next on the bench.
