Velta Relay

pbuzdin/relay is our public fork of chatmail/relay, the software that runs a chatmail mailbox. We track upstream and merge it regularly. The latest merge, pbuzdin/relay#3 on 17 November 2026, brought in twelve upstream commits, including filtermail v0.7.8 and a bounce-queue lifetime of two days, matching the ordinary queue lifetime.

Issues are disabled on the fork, so planned relay work is tracked in the Velta repo — today that is velta#395. The living capability table is docs/compare.md in the fork; VELTA-DEPLOY.md is the overlay index. This page is the public map. The messaging engine on the client is covered on Velta Core.

Upstream’s own documentation for a stock relay is at chatmail.at/doc/relay.

What the fork adds

A stock cmdeploy run gives you a chatmail relay: encrypted mail only, automatic deletion, IMAP and SMTP, optional iroh and TURN. The Velta overlay on top of that is a small set of product choices. They are documented in the fork and, today, still applied as a documented overlay on a deployed box; moving every piece into the cmdeploy templates is tracked work in that same repository.

Invite-only signup
What. Open /new signup is closed. Accounts are minted only with a signed invite — a velta.cc/web link with a use count and an expiry (48 hours if you omit one; never, if you set it to zero). Unsigned links are refused.
Why. A chatmail relay that anyone can join is a different service from one you invite people to. Details: docs/invites.md.
A WebSocket mail tunnel
What. Browser clients tunnel IMAP and SMTP over WebSockets, with an origin allowlist, instead of opening raw TCP — something a browser cannot do.
Why. The Velta PWA has to speak to a relay from the browser. Details: docs/ws-proxy.md.
PWA hosting
What. The relay can serve the Velta web app as static files under its own origin, so the app and the WebSocket endpoints share that origin.
Why. A self-hosted browser client should not have to talk across origins to reach its mailbox.
Incoming and transport filtermail, and HTTPS federation
What. filtermail runs as three services — outgoing, incoming, and transport — and the overlay can accept relay-to-relay mail over HTTPS (/mxdeliv), still requiring DKIM alignment and encryption.
Why. Incoming and onward delivery have different jobs from the outgoing submission filter, and some peers can federate without classic SMTP on port 25.
A dual-line iroh relay
What. The overlay can advertise both the current iroh 0.35 line (what today’s cores, including Delta Chat, use) and an iroh 1.x line, as two metadata values.
Why. Clients on either generation can reach the same operator while the ecosystem moves.
Veltar, the admin bot
What. A chat-driven bot on the relay’s own account can mint invites, report status, and handle other admin tasks. Its source lives in the fork.
Why. Running a relay should not mean SSH for every invitation. Details: docs/admin-bot.md.

Planned work

#395 — Sending reliability is the main tracker. After a message is accepted (SMTP 250), onward delivery still happens later. If that delivery is deferred, the message can sit in the Postfix queue for up to two days, or bounce as a delivery-status notice that Velta usually never surfaces. Two days of silent retry is a poor fit for chat.

The proposal on the fork, and a discussion starter for upstream, is:

  • Shorten maximal_queue_lifetime and bounce_queue_lifetime from two days to about one hour.
  • Set delay_warning_time to about five to ten minutes, so a delay notice can reach the mailbox while the message is still worth retrying somewhere else.

The trade-off is honest: a short remote maintenance window can fail a message that would have gone through later. For chat that is acceptable — the user can retry, including on another relay, once the app shows the delay or bounce and offers #394.

The rest of #395, some of it belonging in upstream chatmail/filtermail or chatmail/relay first:

  • Fix transport stalls and duplicate retries when one slow destination holds a whole delivery transaction (filtermail#252).
  • Reject obviously undeliverable recipients before the relay returns 250, so Velta can try another relay at submit time.
  • Use clearer enhanced status codes (too large, encryption required, unknown domain, retry-after on a rate limit) so the client can tell “this relay will not help” from “try another one.”
  • Report post-accept delays and bounces back to the client, including a stable delivery-status signal the bubble can show.
  • Publish coarse health (size limit, send rate, a public status that does not leak per-destination data) so client-side reputation in #393 has something to read.
  • Don’t spend a rate-limit token on a message that later fails a policy check.

In the fork itself, the documented backlog is to fold the overlay into the cmdeploy templates — including the iroh dual line — so a fresh box does not need hand-applied steps after an upstream merge.

Related client work: #391 (failover and retry in the core), #392 (the per-message picker), #393 (reputation), #394 (retry with another relay).
