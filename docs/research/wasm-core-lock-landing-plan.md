# Landing plan — `core/Cargo.lock` (wasm series)

How the lock diff is reviewed and merged when the wasm series lands in
production `core/` (landing checklist §2, "Landing plan for `core/Cargo.lock`").
The Day-10 analysis below is evidence already gathered via
`cargo tree -i` on the pinned copy for x86_64-linux, aarch64-android and
x86_64-windows; this plan turns it into ordered steps with owners.

## Ordered steps at landing

1. **Freeze the diff.** On the landing branch, `cargo check --locked` must
   fail (lock not yet updated), then regenerate: `cargo check` (unlocked)
   in `core/`, and verify `git diff Cargo.lock` contains ONLY the crates
   above and their transitive pins. Anything else = series drift → stop.
2. **`cargo tree -i` re-run** on the landed tree for the three native
   targets (x86_64-linux, aarch64-linux-android, x86_64-windows) and diff
   against the Day-10 table — any new native-graph entry is a review
   blocker.
3. **Native review (human, non-author):** rusqlite 0.37→0.40 changelog +
   breaking-API sweep (`fallible_uint` adoption sites), SQLCipher 4.14.0
   release notes (security fixes called out), hashlink 0.12.2. The vendored
   crates are reviewed separately (checklist §6 machine diff is done).
4. **Native test pass** independent of wasm: full `cargo nextest run -p
   deltachat --lib` + the Windows sidecar link + smoke (§3) — already green
   on the copy; re-run on the landed tree so the evidence is attached to
   the landing commit.
5. **SQLCipher migration evidence:** attach the Day-11 harness output
   (4.6.1↔4.14.0 round-trip on dbversion 167) to the landing PR; the
   production-Android-DB run rides issue #92.
6. **Release notes:** mention rusqlite 0.40.2 / libsqlite3-sys 0.38.2 /
   SQLCipher 4.14.0 as user-visible dependency bumps (storage engine
   changed), per checklist §2.
7. **Lock hygiene:** the copy's pinned locks
   (`docs/research/wasm-patches/support/locks/`) are regenerated by
   `refresh-lock` AFTER the landing so PROVENANCE matches the landed
   `core/Cargo.lock`; the wasm CI then runs `--locked` against the real
   production lock (apply-on-copy becomes a no-op for locks).
